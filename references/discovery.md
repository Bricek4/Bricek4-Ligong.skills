# 需求探索

只在缺失选择会实质改变结果时进入探索；明确任务不要为形式暂停。

## 六字段结果契约

| 字段 | 要回答的问题 |
|---|---|
| Outcome | 用户最终能观察到什么变化？ |
| Scope | 哪些系统、模块或文件允许受影响？ |
| Invariants | 哪些行为、接口和数据必须保持？ |
| Acceptance | 用什么测试、命令或交互证明完成？ |
| Failure | 错误输入、依赖失败或中断时怎样？ |
| Authority | 是否涉及外部写入、删除、部署或额外权限？ |

分开记录用户事实、安全且可撤销的假设、必须由用户选择的阻塞项。只问一个最小问题；答案未到时继续做不依赖该选择的只读工作。

## 三条设计路径

- **快速路径**：现有调用链和行为确定；内部形成短契约后直接执行。
- **短设计路径**：局部功能有少量真实分歧；在聊天中给 2–3 个方案、取舍与推荐，用户确认后执行。
- **架构路径**：新子系统、公共接口、跨层数据流、权限或迁移；读取 [架构决策](architecture.md)，确认关键取舍后执行。

比较方案时检查正确性、安全、现有架构一致性、实现/迁移成本、可测试/回滚性和长期维护；推荐满足当前目标的最简单完整方案，不预建未要求的能力。

只有以下情况设置确认门：方案会产生不同产品行为；改变公共合同、持久化或兼容承诺；扩大系统/文件/外部动作范围；或产生不可逆后果。其余采用安全默认并在交付中披露。
