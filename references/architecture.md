# 架构决策

架构路径先沿真实调用链建立最小切片，不画与任务无关的通用架构图：入口/解析 → domain/service → repository/schema/migration → response/analytics/Prompt。

架构路径默认 C2；新增子系统、高不确定性、探索任务或用户明确要求高创造性时升级 C3。必须读取 [ForgeLoop SSS 开发协议](forge-loop.md)：C2 比较三个机制，C3 再增加一个 wildcard。先比较再选型；熟悉、流行或“团队一直使用”都不能自动获胜。

## 最低设计内容

1. 组件职责、所有者与依赖方向；每个单元应能独立理解和测试。
2. 输入、状态变化、持久化和输出的数据流。
3. 公共接口的字段、顺序、错误体、状态码与兼容策略。
4. 校验、依赖失败、中断、部分成功、重试和恢复行为。
5. fresh、旧数据升级、重复执行与回滚状态。
6. 身份、租户、权限、隐私和秘密边界。
7. 分层测试、可观察验收和明确非目标。

## 决策规则

- 优先沿用仓库现有稳定模式；只改当前目标需要的边界。
- 先修语义所有者，再同步构造者、消费者、存储、迁移、统计和输出；不能只改接口一端。
- 兼容要求与待删除旧语义分开列账；surface 只投影必须保持的稳定字段。
- 新抽象必须消除当前已存在的重复或耦合；“以后可能用到”不是理由。
- 候选必须在状态模型、数据流、边界所有权或一致性机制上真正不同；参数和命名变体合并为一个。
- 公共合同、持久化、权限和不可逆取舍必须得到用户确认；普通内部实现选择由力工决定并披露。

把每条编号要求映射为“边界/文件 → 实现不变量 → 可观察证据”。找不到 owner 表示调用链尚未走完，不能开始跨层编辑。
